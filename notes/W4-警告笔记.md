## 二、15 条警告逐一解释

### 1. `-Wformat=` （8 条）

**出现在**：`exercises/W3-Day2-pointer-array-relationship.c` 第 8、9、10、11 行

**警告原文**：

```
warning: format '%p' expects argument of type 'void *',
         but argument 2 has type 'int *'
```

**为什么会警告**：

`%p` 要求参数是 `void *`（通用指针），我传的是数组名 `arr`，它在表达式里会退化成 `int *`。两者类型不匹配。

一个容易误解的点：`int *` 转 `void *` 在 C 里是自动允许的，所以这不是"非法转换"，程序也能编过。gcc 之所以警告，是因为 `%p` 遇到非 `void *` 参数属于未定义行为，所以 gcc 把它列为可选诊断来提醒你 —— 提醒的是要显式转换，而不是写错了类型。

**怎么改的**：

```c
printf("arr + 1  = %p\n", (void *)(arr + 1));
```

**踩过的坑**（我自己犯的错）：
一开始我写成 `(void *)arr + 1`，结果触发了新警告 `-Wpointer-arith`。
原因是 `(void *)` 比 `+` 优先级高，`(void *)arr + 1` 会先执行 `(void *)arr`，然后再 `+ 1`。

关键点：`void` 是没有大小的类型，所以这里的 `+1` 只前进 1 个字节，而不是 `int` 的 4 个字节。指针加法走多少字节由指针指向的类型决定，`void *` 无法确定元素大小，gcc 就用 `-Wpointer-arith` 警告你"这么算不对"。

**不改会怎样**：
打印出来的地址会落在元素的中间（偏移 1 字节处），而不是下一个元素的起始地址。也就是说四个地址看起来"只差 1"，但这并不是"元素间距变成 1 了"，而是算出来的地址本身就是错的。

### 2. `-Wdiscarded-qualifiers` （1 条）★ 这个是真 bug

**出现在**：`exercises/W4-Day1-pointer-myMemcpy.c` 第 30 行

**警告原文**：

```
warning: initialization discards 'const' qualifier from pointer target type
```

**错误写法**：

```c
char *s = (const char *)src;      /* const 被丢掉了 */
```

**正确写法**：

```c
const char *s = (const char *)src;
```

**为什么这是真 bug（不只是警告）**：
源指针`const char *src`是只读，加const保护，不允许修改源内容，把这个带const的指针赋值给一个不带const的普通指针s.就意味着可以通这个指针修改数据，这是不安全的。

**结论**：`const` 不是"装饰"，是类型限定符

### 3. `-Wparentheses` （3 条）

**出现在**：
- `exercises/W3-Day4-pointer-strcpy.c` 第 26 行
- `projects/w3-pointer-toolbox/main.c` 第 99、127 行

**警告原文**：

```
warning: suggest parentheses around assignment used as truth value
```

**错误写法**：

```c
while (*dest++ = *src++);
```

**正确写法**：

```c
while ((*dest++ = *src++));
```

**为什么加括号就不警告了**：
while()括号里做的是条件判断，在括号里写一个赋值语句，编译器会担心你是误写，导致条件永远为假或真，加括号表明我确实要用这个赋值的结果做判断

**编译器想防的典型 bug**：

```c
if (a = 0) { }      /* 本想写 a == 0，少打一个等号 */
```
将0赋值给a，而0是假，条件永远不成立

**顺便读懂这一行**（面试常问）—— `while ((*dest++ = *src++));` 展开成普通写法是：

```c
while (1) {
    *dest = *src;                  /* 1. */
    dest++;                        /* 2. */
    src++;                         /* 3. */
    if(*dest=='\0')break;          /* 4. */
}
```

**为什么 `'\0'` 也能被正确复制**：
赋值表达式的值就是“被赋的那个值”，当*dest拿到'\0',它的值为0，条件为假，循环结束

### 6. `-Wsign-compare` （1 条）

**出现在**：`projects/w3-string-processor/main.c` 第 106 行

**警告原文**：

```
warning: comparison of integer expressions of different signedness:
         'size_t' and 'int'
```

**涉及的两个类型**：

| 表达式 | 类型 | 有符号？ |
|---|---|---|
| `strlen(...)` | `size_t` | 无符号 |
| `max_len` | `int` | 有符号 |

**为什么危险**：
C 会把 `int` 转成无符号再比较。如果 `max_len` 是负数，它会变成一个很大的正数，比较结果就完全错了。

**怎么改**：把 `strlen` 的结果显式转换成 `int`。实际改了 3 处：

```c
int max_len = (int)strlen(word[0]);          /* 第 101 行：初始化 */

for (int i = 1; i < n; i++)
{
    if ((int)strlen(word[i]) > max_len)      /* 第 106 行：比较 */
    {
        max_len = (int)strlen(word[i]);      /* 第 108 行：赋值 */
        max_idx = i;
    }
}
```

**顺带的优化**：`strlen` 每调用一次就要从头遍历一遍字符串，上面这个循环对同一个单词调用了 2 次。应该先存下来：

```c
for (int i = 1; i < n; i++)
{
    int len = (int)strlen(word[i]);     /* 只算一次 */
    if (len > max_len)
    {
        max_len = len;
        max_idx = i;
    }
}
```

## 三、两个真 bug（编译器看不出来的）

### Bug ① 栈缓冲区溢出

**位置**：`exercises/W2-Day4-array-char.c` 第 8 行

**错误代码**：

```c
char str[1000];
scanf("%s", str);          /* %s 不限制长度 */
```

**现象**：输入 1200 个字符 → 程序崩溃，退出码 `0xC0000005`

**为什么 `%999s` 而不是 `%1000s`**：
字符串结尾会有'\0',需要留有一个字节

**教训**：用 `%s` 读输入时，给%s加宽度限制

---

### Bug ② 负数下标越界写

**位置**：`exercises/W2-Day4-array-char.c` 第 12 行

**错误代码**：

```c
count[str[i]-'a']++;       /* 假设输入全是小写字母 */
```

**现象**：输入 `abcABC` → 输出 `a:1 b:1 c:1`，大写字母消失

**算一下**：`'A' - 'a' = ` -32 → 下标是负数 → `count[负数]` 访问到数组前面的内存

**为什么这比崩溃更危险**：
`count[-32]` 落在数组前面的内存上。它不会立刻崩溃，而是静默地改掉那块内存里的数据 —— 那块内存可能属于别的变量。

危险之处在于：

- **没有任何报错**，程序照常运行
- 出错的地方和被改坏的地方毫无关系，可能跑几小时后才在别处表现出异常，极难排查
- 在单片机上更严重：如果那块内存正好是硬件寄存器或关键变量，系统行为会直接错乱

**怎么改**：

```c
if (str[i] >= 'a' && str[i] <= 'z')
{
    count[str[i] - 'a']++;
}
```

**教训**：用数组下标之前，要确认算出来的下标在合法范围内

## 四、我的总结（3-5 条）

> 这部分最重要，写你自己的真实感受。比如"哪条最难懂""为什么当时没发现""以后怎么避免"。

1. 数组下标越界，之前只考虑到了向右越界，没有想到向左越界。之后使用数组下标时要仔细考虑下标是否在范围之内
2. 把`(void *)(arr + 1)`写成`(void *)arr + 1`，没有考虑优先级。之后写表达式要演算是否能得到正确的结果

## 六、这两个真 bug 是怎么被发现的

它们都不产生编译警告，所以只能靠专门设计的测试用例抓出来。这一点很关键 —— 面试官问「你怎么保证代码质量」，这就是答案。

| Bug | 能发现它的测试用例 | 为什么普通测试发现不了 |
|---|---|---|
| 栈缓冲区溢出 | 输入超过 1000 个字符（如 1200 个 `a`） | 输入 `hello` 这种短字符串时完全正常，看不出任何问题 |
| 负数下标越界 | 输入含大写字母（如 `abcABC`、`A`） | 输入纯小写时完全正常；而且它不崩溃、不报错，只是静默算错 |

**从这件事学到的测试方法**：

1. 每个数组/缓冲区都要测"边界值" —— 长度 0、长度正好等于容量、超过容量
2. 每个"假设"都要故意打破一次 —— 代码假设"输入都是小写"，那就要专门输入大写试试
3. 不能只看"跑通了" —— 第二个 bug 程序一直"跑得很正常"，错误是静默的
4. 写完想一遍：这段代码在什么输入下会出错？（这是最有效的一步，不用写测试也能抓到大部分问题）
